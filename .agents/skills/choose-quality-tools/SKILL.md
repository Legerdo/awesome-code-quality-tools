# 프로젝트에 맞는 도구 고르기

## 먼저 확인할 것

대상 프로젝트와 이 목록 저장소의 경로를 구분한다. 대상의 `AGENTS.md`와 기존 설정을 읽고 언어, 엔진 버전, 패키지 관리자, 빌드 방식, 실행 OS, 현재 검사 명령을 확인한다. 프로젝트 파일로 알 수 있는 내용을 사용자에게 다시 묻지 않는다.

어떤 문제를 검사할지 먼저 정한다. 예를 들어 미사용 의존성 정리, 레이어 간 참조 제한, 중복 코드 탐지, 변경 영향 파악은 서로 다른 작업이다. 코드 그래프를 린터나 실행 테스트의 대체물로 제안하지 않는다.

## 목록 조회

[조회 스크립트](../../../scripts/query_catalog.py)는 목록을 읽어 JSON으로 출력한다. 아래 명령은 이 저장소 루트에서 실행한다. 분석기를 설치하거나 대상 프로젝트를 검사하지 않는다.

```powershell
python scripts/query_catalog.py --list-profiles
python scripts/query_catalog.py --profile typescript-web
python scripts/query_catalog.py --tool fallow
```

조회 결과의 `reviewed_on`, `verification`, `status`, `limitations`와 라이선스 근거를 함께 읽는다. 조회 스크립트를 쓸 수 없으면 [catalog.json](../../../data/catalog.json)과 [개발 환경별 안내](../../../docs/PROFILES.md)를 직접 읽는다.

## 선택 기준

이미 쓰는 도구가 필요한 검사를 제공하면 우선 재사용한다. 새로운 도구는 어떤 빈틈을 채우는지 설명한다. 기능이 겹치는 도구를 함께 쓰는 것도 가능하다. 결과를 비교할 목적과 CI에서 실패로 처리할 기준을 정하며, 근거 없이 하나만 쓰도록 제한하지 않는다.

`excluded` 항목은 이 저장소의 기본 추천에서 제외한다. `engine-exception`은 해당 엔진과 패키지의 조건을 확인한다. [라이선스 기준](../../../docs/LICENSE-POLICY.md)은 선택한 버전의 LICENSE를 다시 확인하는 일을 대신하지 않는다.

Unreal의 Blueprint 참조, Unity의 씬과 직렬화, Godot의 시그널처럼 소스만으로 확인하기 어려운 경로를 남겨 둔다. 미사용 진단만으로 코드나 에셋을 삭제하지 않는다.

## 제안과 실행을 구분

먼저 도구별 목적, 겹치는 기능, 필요한 설정, 확인한 근거, 아직 검증하지 않은 내용을 표로 제시한다. 사용자가 실행을 요청했다면 설치 상태와 버전을 확인하고 작은 범위에서 시작한다. 기존 설정을 보존하고 자동 수정은 진단과 분리한다.

실행할 때는 [검증 기준](../../../docs/VERIFICATION.md)과 [결과 기록 양식](../../../docs/templates/QUALITY-CHECK.md)을 사용한다. 분석기 오류, 시간 초과, 일부 파일만 검사된 결과를 통과로 바꾸지 않는다.

## 마무리

선정한 이유, 실제 실행한 명령과 결과, 남은 확인 사항만 보고한다. 공식 문서 확인, 실제 설치, 검사 통과를 각각 구분한다. 문서만 읽었다면 도구가 해당 프로젝트에서 동작한다고 단정하지 않는다.
